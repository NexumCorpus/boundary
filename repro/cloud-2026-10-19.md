## README gaps a stranger would hit

1. **Stated hash cannot be verified from a clone.** `683c6239…` is the CRLF hash, but the repo ships LF. Fix: state the LF hash `91564e16…`, or state both and say which is which.
2. **The hash is not in the repo at all.** It appears only in a commit message. Put it in the README or in `claim.json` next to the scores.
3. **Running the check dirties the working tree.** Four `.pyc` files are tracked despite `.gitignore`. Untrack them with `git rm --cached`, so that "nothing changed" can be checked with `git status`.
4. **No expected output in the README.** The README never says what success looks like (11 passed, 5/5 OK, negative control exit 1). Those numbers appear only in the commit message.
5. **`python`/`pip` assumptions.** This VM had both, so neither caused a problem here. On a stock Ubuntu or Debian system, `python` does not exist without `python-is-python3`, and `pip install` is refused with PEP 668 `externally-managed-environment`. A one-line venv alternative would help: `python3 -m venv .venv && . .venv/bin/activate`.
6. **No Python version stated.** CI covers 3.9 and 3.13, and both work here, but the README doesn't say so.
7. **pytest is unpinned.** pytest 9.1.1 works today. The tracked `.pyc` is named for pytest-9.1.1, so the author used the same version, but nothing pins it.
8. **"check.py (unchanged)" cannot be verified.** No reference hash for `check.py` is recorded, so a stranger can't confirm it is byte-identical to the version that was certified. Its sha256 here is `774dda05b39f760aca46bbdb807bb82b56948b094dd05c389fc1cec75f128e44`.
9. **`claim.json` still points at the old location.** Its statement says the recorded scores are at `E:/mission-runs/w2_holdout_results.jsonl`, not the shipped bundle path. This is accurate history, but it may confuse a stranger.
